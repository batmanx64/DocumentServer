# ONLYOFFICE DocumentServer 二开核心指南（仓库识别 / 子模块构建 / Docker 产物）

> 目标：解决 3 个核心问题——
> 1）这个仓库到底怎么组织；2）各模块做什么；3）二开时开发环境如何搭、子模块如何构建、最终如何出 Docker 镜像。

---

## 1. 仓库识别：这是“聚合仓 + 子模块编排”

从根仓 `Readme.md` 和 `.gitmodules` 可以确认：

- `DocumentServer` 根仓是聚合入口，不是单体代码仓。
- 真正可编译业务代码分散在子模块（`server` / `core` / `sdkjs` / `web-apps` / `dictionaries` / `core-fonts`）。
- 插件能力也通过 `sdkjs-plugins/*` 子模块挂载。

**结论**：二开的第一步不是“直接 build 根仓”，而是先把子模块拉齐，再在对应子模块内改与编译。

---

## 2. 各模块职责（按二开关注点）

## 2.1 业务主链路模块

- `server`：后端服务编排与对外服务层（编辑会话、服务路由、协作链路对接）。
- `core`：文档内核与格式转换能力（doc/docx/xlsx/pptx/pdf 等处理）。
- `sdkjs`：编辑器前端 SDK / API 交互层。
- `web-apps`：编辑器 Web UI 与页面应用层。
- `dictionaries`：拼写检查词典资源。
- `core-fonts`：字体资源（渲染一致性）。

## 2.2 插件扩展层

`.gitmodules` 中声明的 `sdkjs-plugins/*`（如 `plugin-ocr` / `plugin-translator` / `plugin-zotero` 等）可作为功能增量扩展点。

## 3. 二开开发环境搭建（核心操作步骤）

> 下述步骤是“可直接落地”的开发前置流程；重点在于把子模块状态固定、可重复构建。

## 3.1 建议基线

- OS：Ubuntu 22.04（团队统一环境最稳）
- 必备工具：`git`、`docker`、`docker compose`、`make`、`python3`、`node`（用于前端子模块）
- 分支策略：`dev` 为集成分支，功能在 `feature/*` 开发

## 3.2 初始化仓库并进入 `dev`

```bash
git clone <your-repo-url> DocumentServer
cd DocumentServer
git checkout dev || git checkout -b dev
```

## 3.3 子模块一次性拉齐（关键）

### Step A：同步子模块配置

```bash
git submodule sync --recursive
```

### Step B：初始化并拉取

```bash
git submodule update --init --recursive
```

### Step C：确认每个子模块已落地（不是空目录）

```bash
git submodule status --recursive
```

### Step D：锁定二开版本矩阵（建议）

```bash
git submodule status --recursive > docs/submodule-lock.txt
```

> 这个 `submodule-lock.txt` 应随二开版本一起归档，避免“同分支不同结果”。

## 3.4 开发机快速体检（避免后续白跑）

```bash
git --version
docker --version
docker compose version
node --version || true
python3 --version
```

## 4. 各子模块“如何构建”：从代码结构反推并标准化执行

由于根仓本身不承载所有构建脚本，正确做法是**对子模块执行“构建入口探测 -> 构建命令执行”**。

## 4.1 先自动识别每个模块构建入口文件

在根目录执行：

```bash
for m in server core sdkjs web-apps dictionaries core-fonts; do
  echo "===== $m ====="
  [ -d "$m" ] || { echo "missing"; continue; }
  find "$m" -maxdepth 2 -type f \( -name "package.json" -o -name "Makefile" -o -name "CMakeLists.txt" -o -name "Dockerfile" \) | head -n 20
done
```

你会得到每个模块的构建入口清单，然后按入口执行：

- 有 `package.json`：优先 `npm ci && npm run build`（或该模块 README 指定命令）
- 有 `Makefile`：优先 `make` / `make release`
- 有 `CMakeLists.txt`：走 `cmake -S . -B build && cmake --build build -j`

## 4.2 推荐的模块化构建顺序（减少联调返工）

1. `core`（内核/转换能力）
2. `server`（后端服务编排）
3. `sdkjs`（前端 SDK）
4. `web-apps`（页面应用）
5. `dictionaries` / `core-fonts`（资源层）

> 原因：通常上层依赖下层能力，先编核心再编 UI，问题定位最快。

## 4.3 二开时最小闭环（建议）

以“改一个前端交互 + 一个后端接口”为例：

1. 在 `feature/xxx` 改 `sdkjs` / `web-apps`。
2. 若接口或转换逻辑变化，改 `server` / `core`。
3. 分别在改动子模块内完成构建。
4. 回到根仓提交子模块指针变化（gitlink）。
5. 在 `dev` 分支做集成测试。

## 5. 二开后如何构建成一个 Docker 镜像（核心路径）

`Readme.md` 明确 Docker 是官方主安装路径，因此建议采用“**源码二开 -> 产物收敛 -> Docker 镜像封装**”三段式。

## 5.1 路径一（推荐）：复用官方 Docker 工程进行封装

1. 先在各子模块完成二开构建，得到可部署产物。
2. 准备 Docker 构建上下文（按团队规范收集二开产物）。
3. 基于 Dockerfile 构建镜像：

```bash
docker build -t your-registry/documentserver:dev-custom-<buildNo> .
```

4. 本地验证：

```bash
docker run -d --name ds-dev -p 80:80 your-registry/documentserver:dev-custom-<buildNo>
docker logs -f ds-dev
```

5. 验证编辑器页面、协作、保存/回调后再推仓库。

## 5.2 路径二：先做系统包，再进镜像

适合企业已有“deb/rpm 制品库 + 镜像流水线”：

1. 子模块构建后产出系统包（deb/rpm）。
2. 在镜像构建阶段安装这些包。
3. 镜像统一打标签（版本 + commit + 日期）。

## 5.3 镜像标签规范（建议）

```text
documentserver:<主版本>-<二开序号>-g<根仓短sha>-<日期>
```

示例：

```text
documentserver:8.3.0-custom12-gf771b20-20260403
```

## 6. 给团队的“核心交付件”清单（必须落盘）

每次二开发布至少沉淀以下文件：

1. `submodule-lock.txt`（子模块 commit 矩阵）
2. `BUILD.md`（本次真实构建命令）
3. `IMAGE_INFO.md`（镜像 tag、基础镜像、启动参数）
4. `CHANGELOG-CUSTOM.md`（二开变更说明）

这样能保证“可回放、可追溯、可审计”。

---

## 7. 常见失败点与直接处理

- **子模块为空目录**
  - 处理：`git submodule update --init --recursive`

- **同样代码在别人机器构不出来**
  - 处理：比对 `submodule-lock.txt` + 工具链版本

- **镜像起得来但功能异常**
  - 处理：先验证子模块产物是否真的进入镜像，再看运行日志
